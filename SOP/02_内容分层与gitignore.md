# 02_内容分层与gitignore / 02. Content Layering & .gitignore

> **English:** A public tech repo should be organized by **knowledge-asset layer** (evidence-level descending), with a strict public/private boundary enforced by `.gitignore` and verified file-by-file.

> **中文：** 公开技术仓库应按**知识资产层次**（证据等级递减）组织，并通过 `.gitignore` + 逐文件校验建立严格的公开/私有边界。

---

## 1. Public / Private boundary / 公开与私有边界

| Layer 层 | Content 内容 | Committed? 入库? |
|---|---|---|
| **Public 公开** | Conclusions, register maps, protocol specs, methodologies, self-authored code 结论、映射、规范、方法论、自写代码 | ✅ yes |
| **Private 私有** | Cracking procedures: packet captures, string dumps, OEM registry snapshots, decryption/credential scripts, reverse-engineering gotchas 取证/破解原文：抓包、字符串dump、OEM注册表快照、解密/取凭据脚本、反编译踩坑 | ❌ no → `_private_不上传/` |

**Convention:** a dedicated **ignored** directory `_private_不上传/` (never uploaded). If you prefer ASCII, `_private_not_upload/`. The key is: **it must be in `.gitignore`** and verified.

**约定：** 使用专用且**被忽略**的目录 `_private_不上传/` 存放永不公开内容。关键点是：**它必须在 `.gitignore` 里**且经过逐文件校验。

## 2. Directory layering by evidence-level / 按证据等级的目录分层

Use a layered structure so readers know what to trust first. 用分层结构让读者知道先信哪层。

```
00_结论_已确证/       L1 conclusions & correction ledger  终局结论 + 纠错台账（先读这里）
01_协议_逆向成果/     L2 protocol spec & EC/ACPI refs（取证原文迁私）协议规范/参考源
02_代码_Windows/     L3 runnable code  可直接运行
03_代码_Linux/       L3 runnable code  可直接运行
04_过程_文档归档/     L4 process docs & history  历史与决策轨迹
_private_不上传/     PRIVATE — .gitignore’ed 不入库
```

> Each layer is more reusable + higher evidence earlier; later layers are process records. 越靠前越接近「可直接采信的结论」，越靠后越接近「过程记录」。

## 3. `.gitignore` must-haves / `.gitignore` 必备项

Edit from the template `templates/.gitignore.mt`. 从模板 `templates/.gitignore.mt` 改。

| Pattern 模式 | Why 原因 |
|---|---|
| `_private_不上传/` | Private directory 私有目录 |
| `_private/` `__private*/` | Alternative names 别名 |
| `__pycache__/` `*.pyc` `*.pyo` | Python bytecode 字节码 |
| `*.log` | Runtime logs 运行时日志 |
| `*.pcap` `*.cap` | Packet captures 抓包 |
| `*.reg` | Registry exports 注册表导出 |
| `*.dll` `*.exe` `*.bin` | Third-party binaries 第三方二进制（一般不随仓） |
| `opencode.db` `session/` | AI session db 会话库 |
| `.DS_Store` `Thumbs.db` | OS junk |
| `.env` `*.pem` `*.key` | Secrets 密钥 |

> ⚠️ But **allow exceptions** for things you DO want (e.g. `assets/donate_*.jpg` donation QR). Use `!` negation carefully. 但要为确实要发布的内容放行（如捐赠二维码）——谨慎使用 `!` 反向匹配。

## 4. Verification: check-ignore per file / 逐文件校验

The single critical concrete step that proved the `_private` boundary was airtight: 被证明能堵死边界的关键一验——逐文件 `git check-ignore`：

```powershell
# List-all ignored check: every file under _private_ must be ignored
D:\PortableGit\bin\git.exe -C "<repo>" ls-files --others --ignored --exclude-standard | Select-String "_private_不上传" | Measure-Object
# or file-by-file (used when the .ps1 had PS5.1 BOM issues, see lessons)
Get-ChildItem "_private_不上传" -Recurse -File | ForEach-Object {
  if (D:\PortableGit\bin\git.exe -C "<repo>" check-ignore -q $_.FullName) { $ok++ } else { Write-Output "NOT IGNORED: $($_.FullName)" }
}
```

**Expected:** 0 not-ignored under `_private`. 预期：`_private` 下被忽略的文件数 = 全部文件数。

> **Lesson (PS5.1 gotcha):** a wrapper `.ps1` may throw syntax errors in PowerShell 5.1 because **UTF-8-without-BOM is parsed as GBK**. Use the file-by-file `git check-ignore` approach above as an offline equivalent. 详见 lessons。

## 5. After merge/迁移 always re-check / 合并迁移后务必复验

- When you re-org directories or add files, re-run the check-ignore audit. 重组目录或新增文件后，重跑 check-ignore 审计。
- Keep the migration **integrity log**: count of files old vs new, "zero loss" claim backed by per-file name comparison. 保留迁移完整性记录（新旧文件数对比、逐文件名校验「零丢失」）。
